ツイ廃マーケター / requirements & design

要件定義 と 設計書

「作りたいプロダクトの価値を欲しがる人を X 上で見つけ、その人のTLに一番溶け込む自分の過去ツイートをTOP出しする」ツールの、 やること・組み立て方・配達方法を1枚にまとめたもの。

01 — REQUIREMENTS
要件定義：何を作るか

🎯 目的・ユーザー

  • 目的：プロダクトの価値に反応しそうな X ユーザーを見つけ、刺さる自ツイートと届け方を提示する
  • ユーザー：自分のプロダクトを X で広めたい個人（＝あなた）。まずは自分用の分析ツール

✅ やること（機能要件）

  • ① 価値抽出：プロダクト説明 → 価値要素（機能/情緒/社会）
  • ② オーディエンス設計：価値を欲する層＋X検索クエリ＋人数
  • ③ 収集：X API で該当ユーザーとツイートを取得（自分のTLも）
  • ④ タイムライン予測：層ごとの話題・型・エンゲージ統計
  • ⑤ ユーザー別TOP出し：自ツイートを類似度＋ネットワークで並べる（中核）
  • ⑥ アクション：表示率を上げる施策（Xアルゴリズム準拠）

⚙️ 品質・制約（非機能要件）

  • 予算：円建てで上限、実費が超える前に自動停止（従量課金の暴発防止）
  • 永続化・履歴：結果を保存し、過去の実行を見返せる
  • 再開：途中で落ちても続きから（席を離れても安全）
  • 日本語：形態素解析なしで動く（文字bigram）／依存パッケージ0
  • 安全：APIキーは端末/サーバ内だけ、公開URLは合言葉で保護
やらないこと（スコープ外）
  • 自動投稿・自動フォロー等の自動化
  • 非公開情報の取得・大量スクレイピング
  • 個人の狙い撃ち・迷惑行為
前提・依存
  • X API（従量課金）＝収集の実データ源
  • Grok/Claude（任意）＝価値抽出・生成の精度向上
  • 公開ツイートのみ・規約と法令の範囲で利用

03 — DELIVERY
配達方式の比較：手元アプリ vs クラウド

観点ダウンロード式（手元）クラウド（Web）
保存(永続化)端末ディスクに自動で残る（分離不要）外部ストレージが必要（GCSバケット）
いつ使える端末を開いた時だけURLで24時間・他端末/他人も
共有その端末の中だけURLを渡すだけ
更新各端末で入れ直しデプロイ1回で全員に反映
作る/運用の難しさやさしい（デプロイ・課金なし）やや高い（デプロイ・課金・監視・セキュリティ）
初心者向き◎（自分用なら最適）△（共有・配布が要るなら）
💡 指針：自分用・その端末で使えればOK ＝ ダウンロード式が一番シンプル（バケットもデプロイも不要）。 常時URLで共有・人に配りたい ＝ クラウド（保存の分離が必要）。中身（頭脳）は完成済みでどちらにも流用可能。

ミニ用語

  • 永続化：電源やインスタンスが変わってもデータが消えず残ること
  • ステートレス：計算する箱が状態(データ)を持たない設計。だから保存は外に置く
  • 論理分離：データ層とロジックを分けること。保存先を差し替えても中身を変えずに済む
  • 要件定義：作る前に「何を・誰に・どこまで(やらないことも)」を決めること
ツイ廃マーケター 要件定義＋設計書（1枚版）。頭脳＝TF-IDF＋コサイン類似度、収集＝X API（予算内で自動停止）。 手元アプリ／クラウドは配達層のみが異なる。
